# Android builds by branch

The shared workflow is [android-release.yml](../.github/workflows/android-release.yml).
It builds the checked-out commit, chooses the toolchain by branch/tag, and needs
neither `ANDROID_KEYSTORE_BASE64` nor an Expo token. Expo builds run directly on
GitHub's runner using prebuild and Gradle; they do not use EAS Build or `eas.json`.

| Source branch | Build | Release tag | Release title | APK filename |
| --- | --- | --- | --- | --- |
| `sortify-kotlin` | Native Kotlin / Gradle | `kotlin-v2.0.0` | Sortify Kotlin v2.0.0 | `Sortify-kotlin-2.0.0.apk` |
| `main` | React Native / Expo prebuild + Gradle | `expo-v1.7.0` | Sortify Expo v1.7.0 | `Sortify-expo-1.7.0.apk` |

GitHub releases share one repository-wide list. The tag prefixes, titles, and
filenames distinguish the two editions. Kotlin releases do not replace the main
Expo edition's **Latest** release. Existing `v1.7.0` and other old releases are
untouched. A version containing a suffix such as `-beta.1` creates a prerelease.

## Install the workflow on both branches

1. Commit and push the Kotlin project and workflow to `sortify-kotlin`.
2. Copy **only** `.github/workflows/android-release.yml` onto `main`, at the same
   path, and commit/push it there. The workflow is self-contained; the Expo branch
   does not need any Kotlin files. Do not merge the Kotlin rewrite into `main`.
3. Ensure GitHub Actions is enabled for the repository. Release publishing uses
   GitHub's automatic `GITHUB_TOKEN` with `contents: write` in the release job.
   No repository signing secrets are required.

These files have been prepared in the local Kotlin working tree; the main branch
and remote repository have not been changed automatically.

Every push to either configured branch uploads an APK and `SHA256SUMS.txt` under
**Actions → Android APK (Kotlin / Expo) → the run → Artifacts**. These filenames
also include the short commit hash. Branch pushes do not create GitHub releases.

You can also use **Actions → Android APK (Kotlin / Expo) → Run workflow**, then
select `main` or `sortify-kotlin`. GitHub requires the workflow on the default
branch before the manual run button is available:
[GitHub manual workflow documentation](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/manually-run-a-workflow).

## Publish a Kotlin release

Set `versionName` in `app/build.gradle.kts` and increase `versionCode` for each
new version. Commit and push those changes to `sortify-kotlin` before tagging.
For the current `2.0.0` version:

```powershell
git switch sortify-kotlin
git push -u origin sortify-kotlin
git tag kotlin-v2.0.0
git push origin kotlin-v2.0.0
```

The tag must point to a commit that contains the workflow and is on the
`sortify-kotlin` branch. The version in the tag must match `versionName`.

## Publish an Expo release

On `main`, update `expo.version` in `app.json` for each new release. Commit and
push it together with the workflow before tagging. For version `1.7.0`:

```powershell
git switch main
git push origin main
git tag expo-v1.7.0
git push origin expo-v1.7.0
```

The tag must point to a commit containing the workflow on `main`; its version
must match `app.json`. The workflow runs `npm ci`, `expo prebuild`, then
`:app:assembleRelease`. The Expo template signs release builds with its debug
key by default. The workflow verifies the APK signature before uploading it.
See [Expo's local release build guide](https://docs.expo.dev/guides/local-app-production/).

## Signing and installation

Android requires an APK signature even when no keystore secret is supplied.
The Kotlin release build uses Gradle's automatically generated debug keystore;
the Expo build uses the debug signing configuration generated by its template.
The build type is **release**, with a bundled app that runs without Metro.
The signing identity is a **debug key**, suitable for testing/sideloading rather
than store publishing. See [Android app signing](https://developer.android.com/studio/publish/app-signing).

Fresh Kotlin CI runners can generate different debug keys. An APK with a new
key cannot update an existing install signed with another key. Both editions
currently use `com.sortify.app`, so they also cannot be installed side by side.
Uninstalling the existing app allows installation but deletes its local app data.
Preserve a private release key if you later need reliable in-place updates or
store distribution; that is separate from this secret-free build setup.

For a local Kotlin release APK:

```powershell
.\gradlew.bat :app:assembleRelease
```

Output: `app/build/outputs/apk/release/app-release.apk`.
